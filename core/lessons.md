# Lessons

What v1 got right by trial, what it got wrong, and what changed in v2 as a result. Section 1 is v1's own record, migrated unchanged apart from three small edits made obsolete or newly relevant by v2. Section 2 is v2's own record, in the same spirit.

## 1. From the reference project

Things learned bootstrapping the reference project, and improvements over what it did.

1. **Write the example instance early.** It found ten schema gaps in one sitting. Nothing else came close.
2. **Decide naming before writing.** The reference project wrote seven docs with numbered names, then moved to `<project>/docs/design/` unnumbered, breaking every cross-reference. Cost: a full consistency pass.
3. **Decide the codename before writing.** Same reason. `{{placeholder}}` churn touches every file.
4. **Add a doc linter on day one.** A script that checks cross-references, section anchors, index freshness, and placeholder leftovers, run in CI and by agents before ending a session. Drift is inevitable; detection shouldn't be manual. Spec: for every `<file>.md §N.M` in any doc, the file exists and has a heading numbered `N.M`; every milestone in `<project>/docs/milestones/` is in its README with the same status; every ADR is in its index; no `{{` or `TBD` outside `<project>/OPEN-QUESTIONS.md`.
5. **One open-questions file.** The reference project scattered them across six docs' final sections; the ADR guide had to re-list them. Collect them in `<project>/OPEN-QUESTIONS.md` with owner and deadline; each doc's section becomes a one-line pointer — and the linter allows TBD only there and in sketch sections.
6. **`<project>/docs/evidence/` from the start.** Exit criteria say "measured"; there needs to be a place for the measurement.
7. **Root `<project>/README.md` for humans.** Agents read `<project>/AGENTS.md`; a person landing on the repo needs three sentences and a link.
8. **Make "Ground" concrete.** "Understand the current state" produces plans against imagined code. List the actions: read these files, grep ADRs, run tests, inspect these packages, write findings before brainstorming.
9. **Verification evidence in the plan.** A ticked box with no pasted test output is a claim, not a fact. The template has a verification log for this reason.
10. **Escape hatch for small changes.** Without it the process is ignored the first time someone fixes a typo.
11. **Nested `<project>/AGENTS.md` for subtrees.** Codex applies them automatically; Claude Code can be pointed at them. Use them for `<project>/docs/decisions/`, and later for packages with their own conventions.
12. **Backfill ADRs from the design docs.** The design docs already contain a dozen hard-to-reverse decisions. Listing them as ADR 0001–00NN on day one means the decisions folder is real from the first session, not aspirational.
13. **Success criteria for the prototype, in the design doc.** Measurable ones. It turns the first milestone's exit from opinion into numbers.
14. **Non-goals section.** Agents will otherwise helpfully build the thing you deferred.
15. **Say what not to build first.** The most visually impressive part of any tool is rarely the most important. Name it and order it late.
16. **Section anchors are contracts.** Once code or other docs cite `§6.1`, renumbering is a breaking change. Append `§6.1a` instead.
17. **Keep `<project>/AGENTS.md` short and pointing outward.** Rules that change behaviour, layout, commands, conventions, don'ts. Everything else is a link. Over 120 lines and agents stop reading it.
18. **Generate milestone files from the roadmap, then make them authoritative.** Never keep checkboxes in two places — and generate the indexes from them.
19. **Turn Part C into a skill.** Running the bootstrap procedure as a guided conversation instead of a copy-paste catches the same mistakes these other eighteen lessons describe, session after session, without relying on whoever is bootstrapping to have read this file first; `skills/bootstrap/SKILL.md` is that skill.

## 2. From v2

Each entry: what went wrong in v1, and what changed.

1. **Game-specific design docs.** What went wrong in v1: the design docs were shaped for one data-driven game (core loop, pillars, tooling doc); a project of a different shape had to hollow out and rebuild half the templates before they fit. What changed: design docs are chosen per profile (`profiles/README.md`); each profile lists its own docs and section outlines (`profiles/<name>.md`), and the data-driven-product profile keeps v1's docs unchanged for the shape they were written for.
2. **Roadmap written once, in full, at bootstrap.** What went wrong in v1: a long roadmap sketched entirely at bootstrap produced detailed exit criteria for milestones far out, which were fiction the moment anything upstream changed. What changed: rolling wave (`core/long-horizon.md §1`) keeps only the current and next milestone `planned`; everything else is a goal sentence in `sketch` until its phase review promotes it, and phases (`core/layers.md §1`) let a long roadmap state per-phase exit criteria instead of pretending to know a distant milestone's shape on day one.
3. **Feature IDs coupled to their milestone.** What went wrong in v1: nothing said what to do when a feature turned out to belong to a different milestone than where it was created; the only options were renumbering, which breaks every citation, or leaving it in the wrong place. What changed: a feature moved to another milestone gets a new ID there; the old plan is marked `moved to M<n>-<nn>` and the old feature line stays, struck through, pointing at the new one (`core/layers.md §2`), so every existing citation to the old ID stays valid.
4. **Hand-maintained indexes.** What went wrong in v1: `<project>/docs/milestones/README.md`, `<project>/docs/plans/README.md`, and `<project>/docs/decisions/README.md` were maintained by hand, which meant they drifted from the files they were supposed to index the first time two people touched the project on the same day. What changed: `tools/check_docs.py --fix` generates all four index files, including the new `<project>/docs/CURRENT.md`, from the individual files that actually carry status (`core/layers.md §4`); none of the four is ever hand-edited again.
5. **No claim mechanism.** What went wrong in v1: nothing recorded that a session had started a feature, so two parallel sessions could pick up the same one without either knowing. What changed: claiming a feature sets its plan to `in progress` and appends a session stamp under `## Sessions` (`core/parallel-agents.md §1`); the linter flags a stale stamp (`W001`), and an agent must not take a feature stamped under 24 hours ago without a human's say-so.
6. **ADR acceptance blocking Close.** What went wrong in v1: a `proposed` ADR needing human acceptance before Close meant a feature could sit finished but un-closeable, waiting on a human's attention for a decision that often did not need deciding that exact moment. What changed: a `proposed` ADR does not block Close unless marked `**Blocking:** yes`; humans accept proposed ADRs in a batch at milestone close instead (`core/parallel-agents.md §4`, `core/long-horizon.md §4`).
7. **No brownfield path.** What went wrong in v1: the whole procedure assumed an empty repository; a project with existing code had nowhere to start except improvising against a kit built for greenfield. What changed: `core/adoption.md §2` gives a seven-step brownfield procedure that recovers architecture, data model, and decisions from the code and its history instead of writing them from a blank brainstorm.
8. **No spike hatch.** What went wrong in v1: a brainstorm that hit a genuinely technical open question — which library, whether an approach even works — had no sanctioned way to spend throwaway code answering it, short of writing a full plan for code that might be deleted. What changed: a brainstorm may end in a spike — time-boxed, throwaway, recorded in the plan's Current state or an ADR, never committed to `main` (`core/lifecycle.md §2`).
9. **No tiers.** What went wrong in v1: every project got the same full file set regardless of size, so a weekend solo build carried the same milestones/plans/decisions machinery as a twenty-milestone team project. What changed: `core/tiers.md` scales the file set to lite, standard, or full, with promotion rules for growing into the next one.
10. **The linter as a spec, not a program.** What went wrong in v1: the linter was a spec describing what a script should check, with no script behind it, so every project either wrote its own or skipped it, and drift went undetected the way it always does without automation. What changed: `tools/check_docs.py` is a real, tested program with a stable error code per check (`E001`–`E010`, `W001`–`W003`) and a test suite covering every code (`tools/tests/test_check_docs.py`).
11. **Unbounded read cost.** What went wrong in v1: a session's Ground step read the milestone, the roadmap, and whatever else seemed relevant, so the cost of starting a session grew with the project's total history instead of staying flat. What changed: `<project>/docs/CURRENT.md` is generated and held under forty lines by construction (`core/long-horizon.md §7`); a session reads `<project>/AGENTS.md`, then `<project>/docs/CURRENT.md`, then its plan, and reads the milestone or roadmap only when actually planning.
12. **The roadmap left unclassified.** What went wrong in v1: its four-kind table — Design, Decision, Progress, Reference — had nowhere for the roadmap to live: it isn't a design doc (no changelog, no status), and it isn't progress (no checkboxes). What changed: Direction is a fifth kind (`core/doc-kinds.md §2`), naming what the roadmap actually is — order and intent, changing at phase boundaries rather than every session.
13. **Status vocabularies missing `moved`, `sketch`, and `dropped`.** What went wrong in v1: a plan superseded by a later approach, a milestone deferred past any near-term planning, or a milestone cut entirely all had no status word that fit, so each project invented ad hoc language for each case. What changed: `core/layers.md §3` gives a complete status vocabulary per object, including `moved` and `superseded` for plans and `sketch` and `dropped` for milestones, so every real state a project reaches has a name the linter can check.
14. **A filename typo in the kit itself.** What went wrong in v1: the v1 file was named the `PROJECT-BOOSTRAP` file, a typo for "bootstrap" carried since the first commit, and nothing caught it because nothing checked citations to it against the filesystem. What changed: `tools/check_docs.py`'s `E001` check resolves every cited path against the filesystem; a linter with that check running against the kit's own repo would have caught the typo the first time anything cited the file by its correct name and failed to resolve.
