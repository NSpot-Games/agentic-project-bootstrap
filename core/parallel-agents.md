# Parallel agents

Several sessions — different agents, different tools, sometimes a human working alongside them — can work the same project at once. The rules here exist so that happens without merge conflicts on shared files and without two sessions quietly overwriting each other's work on the same feature.

## 1. Claiming

A feature is claimed by setting its plan's status to `in progress` and appending a session stamp line under `## Sessions`: `- {{date}}T{{hh}}:{{mm}}Z — {{agent}} — {{branch}}` (`templates/WORKFLOW.md §3`). An agent must not start a feature whose plan is already `in progress` with a stamp under 24 hours old, unless a human explicitly says to take it anyway — the 24-hour window assumes a session that stalled without finishing might still be mid-thought, and a human is the only one who can tell "stalled" from "abandoned." The linter flags any stamp older than the configurable stale threshold (`stale_hours` in `<project>/docs/.check_docs.toml`, default 24 hours) as `W001` — a warning a human can act on, not a hard failure, since staleness alone doesn't prove the work was abandoned. `W001` also fires for a plan that is `in progress` with no session stamp at all: an unstamped claim is at least as suspect as a stale one.

## 2. Generated files

Four files are never hand-edited: `<project>/docs/milestones/README.md`, `<project>/docs/plans/README.md`, `<project>/docs/decisions/README.md`, and `<project>/docs/CURRENT.md`. Each begins with the marker line `<!-- generated by tools/check_docs.py --fix; do not edit by hand -->`, and `python tools/check_docs.py --fix` writes all four from the individual milestone, plan, and ADR files — the only place their underlying status actually lives (`core/layers.md §4`). Hand-editing one of them is forbidden because it is exactly the kind of edit two parallel sessions are guaranteed to collide on: both would be regenerating the same index from files that changed independently, and a hand edit either gets silently clobbered by the next `--fix` or produces a merge conflict on content neither session needed to touch directly. Run `check_docs.py --fix` at Close (`core/lifecycle.md §5`) and commit the regenerated files with the rest of the change; the linter also warns (`W003`) when a generated file has drifted from what `--fix` would produce, so a forgotten regeneration surfaces before it causes a false conflict for the next session.

## 3. Per-milestone plan directories

Plans live under `<project>/docs/plans/M<n>/`, one directory per milestone, rather than one flat directory for the whole project. This keeps `git status` legible once a project has accumulated two hundred plans, and it means two agents working different milestones almost never touch the same directory, let alone the same file.

## 4. Decisions do not block by default

A `proposed` ADR does not block a feature's Close unless it is explicitly marked `**Blocking:** yes` (`core/lifecycle.md §5`). Humans accept `proposed` ADRs in a batch at milestone close instead of one at a time as each feature finishes (`core/long-horizon.md §4`): batching means a human reviews decisions at the one point in the process where they are already re-examining the roadmap, rather than being pulled out of other work every time an agent proposes something, and it means an agent is never blocked mid-feature waiting on a human's attention for a decision that, by default, does not need it yet.

## 5. Branches and commits

Each feature works on its own branch, `feat/M<n>-<nn>-<slug>`. Commit messages start with the feature ID. `main` is always green: a branch merges only once its feature has closed (`core/lifecycle.md §5`), never partway through, so any session that branches from `main` at any time starts from working code (`templates/WORKFLOW.md §4`).

## 6. Conflict recovery

Claiming (`§1`) is meant to prevent two sessions from working the same feature, but it can still happen — a stamp is missed, a human overrides it, or two sessions start close enough together that neither sees the other's stamp in time. When it does, the later stamp yields: whichever session claimed second stops treating its own work as canonical. That session's work is either rebased onto the branch of the session that claimed first, so the two efforts merge into one line of history, or, if the two approaches genuinely diverge rather than duplicate each other, moved to a new feature ID (`core/layers.md §2`) so both pieces of work survive as separate features instead of one silently overwriting the other.
